## What is actually here

**The difficulty curve now ramps tile cost, not magnitude.** `rollTarget()` computes `maxCost` —
the largest tile cost reachable anywhere in `buildCosts`' BFS result for the board's current
unlocks — and ramps a `costCeil` toward it using the same numbers the old magnitude ramp used, now
in tile-cost terms. A small band below `costCeil` keeps the draw from collapsing onto one
deterministic value once it saturates. Two properties fall out for free: with only `+1` unlocked,
`costCeil` saturates at the board's own operator budget, bit-for-bit the old curve; with `x2`
unlocked, `maxCost` is much lower (14 on the opening board, against a 46-cell budget), so the ramp
saturates within about 3 orders of `x2` existing instead of 15, and holds there indefinitely —
`maxCost` is a fact about the board and unlocks, not about how many orders have been filled, so it
no longer goes flat forever the way the old magnitude ramp did. Fillability is untouched — still
draws only from the same BFS-proven-reachable set round 1 built.

**Two design attempts were tried and rejected before this shipped, worth knowing so nobody re-walks
them** (full detail in the notes file): a cost floor derived from the board's own operator budget
collapsed to an unrestricted pool once `x2` existed, because the BFS never produces a cost above 14
regardless of budget; an exact single-cost bucket fixed the averages but collapsed to one
deterministic value forever on a board that never buys anything.

**`Autosave`, `gvb-save.js` adoption, mobile clipping fix, fonts** — all round 1, all unchanged and
still true, see round 1's archived notes for detail.
