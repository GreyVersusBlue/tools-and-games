## House rules for every file in this repo

- **No build step.** Static files served by GitHub Pages from the repo root at
  `greyversusblue.com`. Plain ES modules, no bundler, no transpiler, no runtime npm dependency.
- **Zero offsite requests.** This game now has none — see below.
- **Each project vendors its own copy; nothing is shared across projects** (locked decision #17).
- **Never change a storage key** (locked decision #36). Yours is `integer-foundry-save-v1`. **It
  keeps that name.**
- **`migrate` is for version drift; `repair` is for every load** (locked decision #37).
- **Assert against the DOM for anything that just happened, and against the save only for what a
  reload has to survive** (locked decision #39). This rule was written partly because this game's
  old autosave ran on an eight-second interval, routinely stale relative to the screen. That
  interval is gone — the save is now debounced to 700ms via `slot.autosave()` — but the rule
  itself still holds: assert the DOM for anything just-happened regardless of how fast the save is.
- **A guard-rail that can be satisfied by luck gets seeded, not retried** (locked decision #40).
  This rule used to be illustrated by this game's suite seeding an unfillable target; that seeding
  is gone now that every order is guaranteed buildable, which is the better outcome the decision
  points at.
- **`page.__blocked` is "offsite and refused"; `page.__shimmed` is "offsite and fulfilled locally
  instead"** (locked decision #44). A page can report empty `__blocked` and still hotlink fonts,
  because the font shim answers the request before the blocked-list check runs. This project's own
  round-1 session found this independently before it was formalized; `check-integrity.mjs`'s
  static source sweep is now the check that actually catches it, and running it is faster than
  grepping the page by hand.
- **`repair` also covers content drift, not just schema drift** (locked decision #50).
- **Windows is the dev machine** (v7 §7). An absolute `import()` path needs `pathToFileURL`.
- **A check that only prints is a check that gets ignored** (locked decision #13).
- **Verify a guard-rail by reintroducing the bug it guards** (locked decision #34).

## What is actually here

`Projects/integer-foundry.html` is 1023 lines, 40 KB, plus a folder: `js/targets.js` (199 lines),
`js/state.js` (226 lines), `test/smoke-targets.mjs` (90 checks) and `test/browser.mjs` (56 checks),
`fonts/` (six vendored woff2 faces), and a `README.md`. Tagged `Puzzle` and `data-new` on the
board, with a preview and OG card. The URL did not change: still
`/Projects/integer-foundry.html`.

**The order generator now guarantees a fillable target.** `js/targets.js` runs a real BFS over the
integers reachable from 1, one step per operator tile, bounded by the board's actual spare cells
and the existing 300-value cap. `rollTarget(state)` keeps the old difficulty ramp but clamps the
ceiling to what the board can build and draws from the reachable set instead of a bare integer
range. The old generator let the worst-case roll exceed the board's actual ceiling of 47 from the
twelfth order onward (measured: 51% of rolls unfillable at 30 orders filled, 2698 of 5000). The new
one measures 0 of 5000 unfillable at the same point. The sink's tooltip now also states what an
order actually needs, e.g. "Order 47: 46 fabricators between a source and this sink."

**Autosave is debounced, not on a timer.** `slot.autosave(getState, 700)` from `gvb-save.js`
replaced the old `setInterval(save, 8000)`: dirty-marked on every change, written at most once per
700ms, flushed on tab-hide. A save is now under a second behind the screen instead of up to eight,
and rotating a placed tile (which used to skip the save until the next 8-second tick) now persists
immediately.

**`gvb-save.js` is adopted.** `Projects/integer-foundry/js/state.js` holds the state shape,
`validState`, `repairState` and the slot. Key unchanged: `integer-foundry-save-v1`. Version stays
1. `repair` fixed four real bugs found in the process: a grid whose `cols`/`rows` disagreed with
the actual `grid` array shape (previously crashed the page before the first frame on a narrower
grid, silently clipped columns on a wider one); `unlocked`'s nested fields never reached by a
shallow merge; two sink tiles able to share one `sinkIndex` silently; and `prestigeMult: null`
becoming `0` rather than `1` via `Number(null)`, which zeroed every future payout permanently. The
save bar is mounted in the sidebar, reachable during play, with `buttons: ['export','import','reset']`
and no `filename`/`labels` overrides.

**Mobile clipping is fixed.** `cellPx` used to be hardcoded near its max (58px) regardless of
viewport, silently clipping the right-hand columns off a 375px phone screen with no way to scroll.
It is now measured from the actual frame, clamped 18–58px, and recomputed on resize, load and
floor growth.

**Fonts are vendored.** Inter, JetBrains Mono and Oswald, six woff2 files in `Projects/integer-foundry/fonts/`,
116,508 bytes. Zero `fonts.googleapis.com` references in the page.

**Test suites exist and pass.** `node Projects/integer-foundry/test/smoke-targets.mjs` — **90
checks, 0 failed**. `node Projects/integer-foundry/test/browser.mjs` — **56 checks, 0 failed**
(if a frame-motion assertion fails once and passes on retry with no other change, that is Chrome
throttling an unfocused window, per the one-suite-at-a-time note below, not a finding).

## Your task

**Task one, the headline: revisit the difficulty curve.** Round 1 deliberately left this alone —
"the curve is linear in orders filled and the shop is not... changing the ramp and clamping it in
the same session would have made the clamp impossible to attribute if the game started feeling
wrong." That reasoning no longer applies; the clamp has shipped and been verified on its own for a
full round. The opinion already on record: there is a stretch around 15–30 orders where targets
climb by 3 each time while `x2` (an 80-ingot shop purchase) has already flattened the difficulty to
nothing. Worth asking on its own now: is this a good curve? Candidates worth weighing — tying the
ramp to what has actually been unlocked/bought rather than only to orders filled, or smoothing the
climb so `x2` doesn't trivialize a 15-order stretch immediately after it's bought. This is a design
call, not a correctness bug — say what you'd change and why, and if you change it, verify the
existing 90+56 checks still pass and that the guaranteed-fillable property from round 1 is untouched.

**Task two, if there is session left: the two conservative model gaps round 1 named and chose not
to fix.** Both are safe-direction (they make orders easier than they need to be, never harder), so
neither is urgent, but both are candidates if the curve work above doesn't fill the session:

- Mergers and splitters are left out of the BFS model entirely, so a player who buys `Merge x`
  (420 ingots) without `x2` (80 ingots) keeps getting orders capped at 47 on a floor that could
  reach roughly 529.
- `opBudget` divides the floor by the number of sinks actually placed, which is conservative but
  crude — two lines sharing a prefix through a splitter don't really halve the board's capacity.

Neither is a correctness bug (the game never hands out an unfillable order either way), so treat
these as refinements to the reachability model, not fixes.
