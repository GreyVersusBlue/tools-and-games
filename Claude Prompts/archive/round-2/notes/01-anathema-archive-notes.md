## What I verified

  - Neutered the "clicking the anchor again clears" branch in the shard-bar click handler (`else if (false && l === S.lvlAnchor)`). Result: 3 direct failures (anchor didn't clear, fresh-anchor-after-range didn't start, its range didn't clear) plus the shard-sync test aborting on a timeout waiting for shards to unload, since that path depends on the same clear.

  - Both times, the rest of the suite (level-bar test's first half, hash-routing, bookmark resolution) kept passing, which is itself useful: it means the failures are localized to the sabotaged logic, not the harness cascading unrelated red.
- **`renderNpc` sweep for the round-1-flagged "structured data duplicates baked-in prose" bug class** (task 2): wrote a one-off Node script (not committed — see "Deliberately not done") that loaded all 26 npc shards (6,393 creatures) and checked, for every creature with non-empty `system.details.publicNotes`, whether that prose independently restates the AC, HP, Speed, or Perception value the app also prints from structured fields — the same shape as the spell-heighten bug (structured field synthesized independently of prose that already said the same thing).
  - **Result: zero real duplicates.** 4,236 of 6,393 creatures have non-empty `publicNotes`. One coincidental string match turned up (Watcher, AC 48) — checked by hand, and it's the Beacons of Jandelay's AC mentioned in lore text, not the Watcher's own AC restated; not a duplication bug.

Every `kv()` call in `renderNpc` is a direct format of a structured stat-block field (AC, HP, saves, skills, speed, resistances) — there's no separate narrative-synthesis step that could duplicate an already-written sentence, which is what actually caused the spell bug. The bug class round 1 flagged as "most likely to hide here" doesn't have a foothold in this renderer's code shape. Confirmed with real numbers rather than left as an assumption, per the site's own "measure, don't guess" convention.

## Deliberately not done

- **The `renderNpc` data-sweep script isn't committed.** It was a one-off read-only analysis (load every npc shard, check for AC/HP/Speed/Perception duplication in prose) to answer a specific question, not a reusable check — there's no ongoing invariant here to guard, since the answer was "this bug class doesn't structurally apply to this renderer." If a future session wants to re-run something like it, the approach was: for each creature with non-empty `system.details.publicNotes`, regex the structured field's value against the prose with a word boundary (`\bac\s*48\b` etc.) and hand-check any hit — the false-positive rate is real (see the Watcher case above), so hand-checking hits matters more than the regex itself.
- **Not touching `newindex.html` or `index.html`.** Both outside this project's boundary; see "What I verified" and "Shared-file requests" above for why neither got a shared-file request instead.
- **Not adding a `package.json` under `Pathfinder/tests/`.** The new suite imports `playwright-core`/`puppeteer-core`/`@sparticuz/chromium` indirectly through `Tools/board-check/harness.mjs`; Node resolves those bare specifiers relative to `harness.mjs`'s own location (which has the `node_modules` that ships them), not relative to the importing file. No dependency of its own to declare, so no manifest to add.
- **Not re-litigating the `gvb-save.js` decision or the file-split question** from round 1's notes — both are still current per that session's reasoning and nothing this session found changes either call. See prior notes (preserved under `Claude Prompts/archive/`) if this needs revisiting.
