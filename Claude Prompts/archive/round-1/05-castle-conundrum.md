## House rules for every file in this repo

- **No build step.** Static files served by GitHub Pages from the repo root at
  `greyversusblue.com`. Plain ES modules, no bundler, no transpiler, no runtime npm
  dependency.
- **Zero offsite requests.** This game already makes none, and unlike most of the repo
  that is actually true here — it hotlinks no fonts and no CDN. Don't regress it.
- **Each project vendors its own copy; nothing is shared across projects** (locked
  decision #17).
- **`libs/addons/` mirrors three.js's own `examples/jsm/` layout** — `loaders/`,
  `controls/`, `utils/` — rather than flattening addon files (locked decision #18).
  Do that again for any new addon whose own imports are relative; flattening means
  hand-patching a vendored third-party file's import paths, which silently rots.
  `Tools/board-check/three-0.160.0/` and `three-0.169.0/` are already-on-disk,
  npm-authoritative copies to source from (locked decision #19).
- **`Tools/` is capitalized, including `board-check` inside it** (locked decision #14).
  Windows hides this; git and GitHub Pages do not.
- **Windows is the dev machine** (v7 §7). An absolute `import()` path needs
  `pathToFileURL`; a bare `C:\...` is read by Node as URL scheme `c:` and refused.
  Don't lean on shell brace expansion either (v6 §5).
- **A check that only prints is a check that gets ignored** (locked decision #13).
- **Verify a guard-rail by reintroducing the bug it guards** (locked decision #34).
  This rule was written *about this project*: two versions of the line-of-sight check
  passed the full suite while doing nothing at all, and the only thing that caught
  either was moving the Guard back into the wall. If you add a check, break the thing
  on purpose and watch it fail.

## Project-specific rules you must not relitigate

These are locked. Read the reasoning in the handoff sections cited before you form an
opinion, and if you still disagree, put it in your notes rather than acting on it.

- **#15** `modelPath` on an NPC def is honoured generically in `npc.js`. The class does
  not hardcode which model belongs to which NPC id. Assigning a real model is a
  `data/npcs.json` edit, not a code change. Don't special-case NPC ids in `build()`.
- **#16** `getDialogueLines()` returns the raw array with the `{RIDDLE}` token intact.
  Substitution is `quest-manager.js`'s job. Moving it into `npc.js` would either
  double-substitute or desync from `quest-manager.js`'s own `hasRiddleToken` check,
  which greps for that same literal string.
- **#21** The casting is `King`→Guard, `Adventurer`→Scholar, `Farmer`→Wizard, **and the
  filenames are actively misleading about why.** v5 §1 has the visual reasoning. If
  you want to revisit it, render the three models first — reasoning from names alone
  produces a worse answer.
- **#22** `hideMaterials` / `hideNodes` on an NPC def are the sanctioned way to subtract
  from a cast model. Generic, data-driven, no NPC id consulted. Use them rather than
  editing a vendored `.gltf` or special-casing in code.
- **#23** Anything rigged goes through `loadGLTF()` and clones via `SkeletonUtils`.
  **Never `Object3D.clone()` a `SkinnedMesh`** — the copy keeps the original's skeleton
  and silently refuses to animate. The mixer runs, the clip advances, nothing moves.
  This is the single most confusing failure mode in the project's history.
- **#24** Held props are aimed from rig geometry, tip following the fingers. The mean of
  the hand bone's child bone offsets points out through the fingers and the prop's
  heavy end goes *that* way. The opposite direction reads as more natural and puts the
  whole prop inside the arm.
- **#26** NPC positions get checked against geometry, not just against the interact
  prompt. Interaction is proximity plus facing with **no line-of-sight test**, so the
  prompt appears happily for a body sealed inside a wall.
- **#27** `play-castle.mjs` runs **headed on purpose**. Don't optimise it back to
  headless: pointer lock and GPU rendering both need real compositing, and the failure
  mode is a hang, not an error.
- **#33** Occlusion tests go against the mesh tree, not `castle.colliders`. Decorative
  geometry can be `noCollide` — the gate arch is — so the collider list is not a
  description of what you can see through.
- **#35** Direct `camera.rotation` writes only work where `PointerLockControls` does.
  This project owns the camera's rotation and rewrites it every frame, so use `lookAt`,
  and prefer it over `turnBy` because Playwright clicks under pointer lock silently
  accumulate yaw and pitch drift.

It has its own end-to-end play test, `npm run play` (`Tools/board-check/play-castle.mjs`

## Your task

**This project has the clearest backlog in the repo. Three known items, all open:**

**Task one, and it is the headline: the wall textures read blurry.** v6 §8 opened it,
v7 §8 says "still not fixed", and v7 §11 lists it third with "budget a session; it is
still the biggest visual win available". The diagnosis in v6 §8 is that it is UV work
or texture-sourcing work. Do the diagnosis properly before you start editing:

- Find out *which* it is. A blurry wall is either a texture whose source resolution is
  too low for the surface area it covers, or a UV mapping that stretches a fine
  texture across too much geometry, or a sampling problem (missing mipmaps, wrong
  `minFilter`, `anisotropy` left at 1, `colorSpace` wrong). Those have different fixes
  and only one of them is about buying bigger images.
- **Measure before deciding an asset is too heavy** (locked decision #42). That rule
  exists because a size estimate that was wrong by 4× blocked the Golden Hour sand
  decision for two sessions. If the answer is "source a higher-resolution texture",
  get the actual byte count before arguing about it. This repo already carries 178 MB
  of assets in this one folder; the bar is lower than you think.
- `npm run play` plus a preview capture give you a real before/after. Take the before
  screenshot first.

**Task two: the Scholar clips through a hall table.** v7 §8, "still cosmetic, still not
fixed". Visible in `Tools/board-check/shots/play/`. Remember locked decision #26 — the
fix is checked against geometry, not against whether the interact prompt appears.

**Task three: the interior braziers read as floating / unsupported.** Same section,
same status, also visible in `shots/play/`.

**Then, if there is session left: audit and plan.** Write a prioritized plan into your
notes for what comes after these three. Worth an opinion:

- **Does this game save at all?** Nothing in the handoffs says it does, and
  `assets/js/gvb-save.js` exists precisely so a project doesn't hand-roll it. A castle
  puzzle you can't leave and come back to is a shorter game than it needs to be. If
  you adopt the module: keep whatever storage key already exists if one does (locked
  #36), pass `defaults` as a factory if any initial state is randomised, put fill-ins
  in `repair` rather than `migrate` (locked #37), and put the save bar somewhere
  reachable during play rather than only on a start screen (v7 §9 is a whole section
  on getting that wrong). A missing hook is a Shared-file request, not an edit.
- **178 MB of assets.** How much of it ships to a visitor? A `.gltf` in the repo that
  nothing loads is dead weight in a clone but free to a browser; a 4K texture on a wall
  nobody sees up close is not. Numbers.
- **Performance.** Frame time, draw calls, whether the castle is instanced.

- `npm run social:check` → 23 notices, 23 already current.
- For the texture work specifically, a before/after screenshot pair is the deliverable.

Scheduling note that will cost you a run if you skip it: `npm run play`, `npm run
games` and `npm run previews` all open real visible browser windows, and **Chrome
throttles a window nobody is looking at.** v7 §6 is a whole section about a
seven-game run that failed twice and passed on retry because someone clicked another
application: the render loop stalls and keyboard input moves nobody, so a walk
assertion covers no ground and two "is the frame moving" screenshots come out
byte-identical. `harness.mjs` now launches with `--disable-backgrounding-occluded-
windows`, `--disable-renderer-backgrounding` and `--disable-background-timer-
throttling`, which fixed it. Two of these suites running at once in different threads
will still steal focus from each other. Only one at a time. If a frame-motion or walk
assertion fails once and passes on retry, this is the first thing to suspect, and check
the flags survived.
