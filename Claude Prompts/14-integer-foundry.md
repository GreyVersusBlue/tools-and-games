## What is actually here

935 lines in one file, 34 KB. Tagged `Puzzle` and `data-new` on the board, with a preview and OG
card. `SAVE_KEY = 'integer-foundry-save-v1'` at line 285, hand-rolled `localStorage` in three
places (lines 334, 340, 918) with no version stamp and no validation — a corrupt blob is
`JSON.parse`d straight into state and the game boots on it.

`npm run games` drives it: builds an 8-tile production line, watches the sink judge what arrives,
reloads, and fills an order.

**Two things about this game cost the suite a run, and both are worth understanding as bugs rather
than as test problems.**

**One: the sink can ask for a number the board cannot produce.** From v7 §3 verbatim: "Integer
Foundry's sink asks for a number up to 12 and a straight 8-cell row only holds six `+1`s, so 'did
it pay out' is unassertable as-is." The suite's fix was to write `sinks[0].target = 3` into the
save and reload.

Read that again as a player rather than as a tester. **The game can generate an order that cannot
be filled.** Whether that is fatal depends on whether the board is really limited to a straight
8-cell row in normal play, or whether the suite was building the simplest possible line and a real
player has more room — find out, because those are different bugs with different fixes. If a
player can hit an impossible target, that is the most important thing in this file. If they can't,
then the reachable range is board-dependent and the target generator should know about the board
rather than picking from a fixed 1-to-12.

**Two: the autosave fights anything that writes to the save.** The suite had to neuter
`localStorage.setItem` on the outgoing page before reloading, "because its autosave is still armed
and will write the old target back". An eight-second interval autosave that can clobber a
deliberate write is also a hazard for a player: any state change in the last eight seconds before
a close is lost, and any state written by something other than the autosave can be overwritten by
it.

**It hotlinks three Google Font families** — Inter, JetBrains Mono and Oswald — at line 25. v7 §5
claims the site makes zero offsite requests site-wide. That is wrong for fifteen pages, and the
suite cannot see it: `prepPage()` in `Tools/board-check/harness.mjs` *fulfills* Google Fonts
requests locally from bundled `@fontsource` packages before the blocked-list check runs, so font
hotlinks never reach `page.__blocked`. All three families are already on disk in
`Tools/board-check/node_modules/@fontsource/` — copy woff2 files out, but nothing at runtime may
reference `node_modules`.

## Your task

**Task one, the headline: fix the target range so the sink cannot ask for the impossible.**

Do the diagnosis before you pick a fix:

1. **Determine the actual reachable range** for a given board, properly. Not by playing until it
   feels right — work out what the maximum achievable value is as a function of board size and
   available tile types, and check it against play.
2. **Determine whether a real player can be handed an unreachable target**, or whether it only
   happens on a minimal board the suite happened to build. Say which, with evidence.
3. Then fix it. The likely shape is that target generation becomes a function of the board rather
   than a fixed 1-to-12 roll — which also means the game can guarantee solvability, which is a
   better property than "usually fine".
4. **When it is fixed, `play-games.mjs` should no longer need to seed `sinks[0].target = 3` or
   neuter `setItem` to test the payout.** That removal is a Shared-file request. Write it precisely:
   which lines come out, and what assertion replaces them. Locked decision #40 exists because a
   guard-rail satisfiable by luck must be seeded rather than retried — the better outcome is that
   luck stops being involved.

**Task two: fix the autosave.** An eight-second interval is a compromise nobody chose deliberately.
Options worth weighing: save on state change with a short debounce instead of on a timer, so the
save is never more than a moment behind the screen; or keep the timer but also save on
`visibilitychange` and `beforeunload` so a close doesn't lose the last eight seconds. Note that
locked decision #39 was written partly because of this timer, and if the save stops being stale
that rule's example changes — say so in your notes, because it affects how the suite should be
written.

**Task three: adopt `assets/js/gvb-save.js`.** Three hand-rolled `localStorage` calls with no
version stamp and no validation is exactly the shape the module exists to replace. You get file
export and import, a memory-backed fallback for browsers that block storage (reading the
`localStorage` property *throws outright* there), and validation. Specifics from v7 §1:

- **Keep the key `integer-foundry-save-v1`** (locked decision #36).
- **`defaults` may be a factory** — if a new game rolls a board or a target, pass a function or
  `slot.reset()` hands back `null`.
- **Fill-ins go in `repair`, not `migrate`** (locked decision #37). `repair` runs on every accepted
  load from every door; `migrate` only on version drift. Go looking for a field added since the
  game shipped that an old save lacks and that lands in arithmetic — that is the bug class, and in
  The Fourth Quarter it produced an NPC with a NaN speed that never arrived anywhere, with no error
  at all.
- **`mountSaveBar` takes a `buttons` option** and each button carries
  `data-gvb="export|import|reset"`. **Put it somewhere reachable during play**, not only on a title
  screen — v7 §9 has an item open for exactly that mistake elsewhere.
- **Adopting the module also settles the autosave question**, because the module owns the write
  path and the "autosave clobbers a deliberate write" problem stops being yours to solve twice.
- **A missing hook is a Shared-file request, not an edit** to `gvb-save.js`.

**Task four: vendor the three fonts.** Inter, JetBrains Mono, Oswald. Local `@font-face`, woff2 in
a folder you own, hotlinks deleted, only the weights the page uses. README naming source and
licence. Measure and report the total (locked decision #42).

**Task five, if there is session left: audit and plan.** Worth an opinion: whether there is a
difficulty curve across orders, whether the tile set has enough expressive range, whether 935 lines
should stay one file (a restructure breaks `/Projects/integer-foundry.html`, so the board `href` is
a Shared-file request and you should say the old URL breaks), and mobile at 375×812 — a
drag-and-place puzzle is either good or unusable on a phone with very little in between.

## Verification

This game has no test suite of its own. Given you are about to change target generation and the
save path, it should get one — put it in a folder you own and make it exit non-zero on failure
(locked decision #13). The reachable-range calculation in particular is pure arithmetic and is
exactly what a Node test is for.

- **Save a file written by the current build before you start editing.** You will need it to prove
  old saves still load.
- `cd Tools/board-check && npm run games` → currently 94 checks, 0 failed. **Run it after every
  change**, and expect it to need updating: it seeds your save and neuters `setItem`, so changing
  either the target generator or the save path may legitimately break it. **A break there is a
  Shared-file request, not a reason to revert.** Say clearly in your notes which beats you expect
  to fail and why.
- **Read the DOM, not the save, for anything just-happened** (locked decision #39). Your autosave
  interval is the reason that rule exists. If you fix the interval, re-check whether it still
  applies to you and say so.
- Test the save round trip by hand: play, reload, same state. Export, clear storage, import, same
  state. Corrupt file, refused.
- After vendoring, grep the file for `fonts.googleapis.com` → zero hits. `page.__blocked` is
  **not** the check; `prepPage()` fulfills those requests.
- `npm run check` → 235 units, 0 broken, 0 collisions. `npm run social:check` → 23 notices, 23
  already current.
- **Locked decision #34, and it matters most here:** for the target-range fix, construct the
  impossible-target case on purpose and watch the new guard catch it. A fix you cannot demonstrate
  failing before is not a verified fix.
