## House rules for every file in this repo

- **No build step.** Static files served by GitHub Pages from the repo root at
  `greyversusblue.com`. Plain ES modules, no bundler, no transpiler, no runtime npm
  dependency.
- **Zero offsite requests.** This game already makes none and hotlinks no fonts — one of
  the few pages in the repo where that is genuinely true. Don't regress it.
- **Each project vendors its own copy; nothing is shared across projects** (locked
  decision #17). This project and Aphelion both happen to be on three@0.160.0 and their
  `libs/three.module.js` are separate files on purpose.
- **Never change a storage key** (locked decision #36). Yours is `fq3d-save` and it stayed
  the same through last session's adoption specifically so every campaign saved by an
  older build still loads. Those saves carry no version stamp, which `normalize()` reads
  as version 0.
- **`migrate` is for version drift; `repair` is for every load** (locked decision #37).
- **Import `gvb-save` relatively** — `../../../assets/js/gvb-save.js`, not
  `/assets/js/gvb-save.js`. `test/smoke-campaign.mjs` imports `campaign.js` under plain
  Node, which cannot resolve a leading slash. This is already correct; don't "tidy" it.
- **Nothing in this project touches `localStorage` directly any more, including
  `main.js`.** Reading that property throws outright in a browser configured to block
  storage, which is the exact case the module's memory fallback exists to survive. That is
  why `campaignSlot()` takes no argument in the game and lets `gvb-save` do the probing.
  Tests pass a stub. Keep it that way.
- **Anything rigged goes through `loadGLTF()` and clones via `SkeletonUtils`** (locked
  decision #23). Never `Object3D.clone()` a `SkinnedMesh`.
- **Direct `camera.rotation` writes only work where `PointerLockControls` does** (locked
  decision #35). This project owns the camera's rotation and rewrites it every frame, so
  use `lookAt`, and prefer it over `turnBy` because Playwright clicks under pointer lock
  silently accumulate yaw and pitch drift.
- **Windows is the dev machine** (v7 §7). Absolute `import()` paths need `pathToFileURL`.
- **A check that only prints is a check that gets ignored** (locked decision #13).
- **Verify a guard-rail by reintroducing the bug it guards** (locked decision #34).
- **Assert against the DOM for anything that just happened, and against the save only for
  what a reload has to survive** (locked decision #39).

## What is actually here

Ten `js/` modules, nine vendored texture sets, a real audio folder, its own three.js, and
two Node suites: `test/smoke-campaign.mjs` (137 assertions) and `test/smoke-engine.mjs`
(179). Tagged `Sim` on the board with a preview and OG card.

**It is the shared save module's only adopter.** `js/campaign.js` persists through
`assets/js/gvb-save.js` on the key `fq3d-save`. The start screen has Export save / Import
save under New Game, mounted as `mountSaveBar(..., { buttons: ["export", "import"] })` —
`"reset"` is deliberately omitted because the screen has shipped a "New Game (wipe save)"
button since long before the module existed, and mounting "Start over" beside it would put
two campaign-erasers side by side.

`npm run games` drives the whole save story here: bar present, ladder warps, export,
reload, import, legacy save, New Game, doors open. Two traps in that suite worth knowing
because they are about your code:

- **A file picker has to be answered before it is opened.** `promptImport()` creates a
  hidden `<input type="file">` and clicks it. Playwright wants
  `page.waitForEvent('filechooser')` registered *before* the click; Puppeteer wants
  `waitForFileChooser()`. `prepPage()` sets `page.__engine` so a script can tell. The
  export side needs no engine knowledge — hooking `URL.createObjectURL` reads the exact
  bytes a download would have written, and neutering the anchor click stops the browser
  saving a file. If you change how import is triggered, that suite breaks, and fixing it
  is a Shared-file request.
- **`games.mjs` no longer clicks `#wipeBtn`** to get a clean start. `enter()` clears the
  storage key *before the page that reads it boots*, then reloads. Clearing without a
  reload does nothing, because the module has already read the save and built its
  campaign. Also, this game's entry recipe carries `start: false`, because the save bar
  lives on the start overlay and the regression suite needs it up while a screenshot needs
  it gone.

Two bugs were fixed here last session, both found by adopting the module. Read v7 §2 for
the full story; the short version is that `#startTag` had been quietly lying about what
day it was for anyone who moved venue, and a staffer saved before roles existed loaded with
no walking speed and became a floor NPC with a NaN speed that never arrived anywhere.

## Your task

**Task one, the headline, and it is item 2 on the handoff's next-session list: move the
save bar somewhere reachable mid-campaign.**

The problem, from v7 §9: the save bar is only on the start screen. Exporting a campaign
mid-week means reloading the page to get the start overlay back. Everything is saved by
then so nothing is lost, but it is a step nobody should have to think of. It was left alone
last session because it is a design call about a screen that currently has one button on
purpose.

The handoff already has an opinion about where it goes: **the box score, next to Tomorrow's
Ledger** — that is the natural "I'm done for tonight" moment. Start there, but look at the
screen before you commit; you can see it and the handoff author was reasoning from memory.

Things to get right:

- **Keep the start-screen bar too, or don't, but decide deliberately.** Two bars is fine if
  they're the same component; two *different* export affordances is not.
- **`buttons: ["export", "import"]` stays** on the start screen for the reason above — two
  campaign-erasers side by side is the thing that option exists to prevent. On the box
  score there is no wipe button, so `"reset"` might be appropriate there. Think about
  whether "Start over" mid-campaign is a footgun.
- **Import mid-campaign is the interesting case.** Importing a save while a night is in
  progress means discarding live state. Does the game handle that, or does it need to
  return to a known screen first? This is the actual design work in this task.
- Each button carries `data-gvb="export|import|reset"`, which is how a driver clicks it
  without depending on label text or order. **Keep that on the new bar** and say so in your
  notes, because `play-games.mjs` will want to use it and that is a Shared-file request.

**Task two: the legacy-save audit, generalised.** `repairCampaign()` now derives a missing
`speed` from `skill`, because that field was added after some saves were written. That was
found by accident. **Do it on purpose for everything else.** Enumerate every field added to
the campaign or staffer shape since the game shipped, check whether an old save would have
it, and check whether it gets used in arithmetic where `undefined` becomes NaN. The
symptom class is nasty: no error, no crash, just something that never arrives anywhere.
Both suites should assert each one you find.

**Task three, if there is session left: audit and plan.** Write a prioritized plan. Worth
an opinion: whether the venue ladder (Corner Tap → Fieldhouse → beyond) has enough
distinct feel per tier, whether the night loop has a difficulty curve, frame time and draw
calls with a full floor of patrons, audio mix, and mobile — this is a pointer-lock 3D game,
so "mobile" may honestly be "not supported", which is a legitimate answer to write down.
